## 1. Проблема

Исследователь задаёт сложный вопрос одной LLM — получает один ракурс. Если вопрос спорный, модель либо даёт «сбалансированный» ответ (усреднённый, неглубокий), либо уходит в одну позицию без контраргументов. Переключение между моделями вручную (открыть Claude → открыть ChatGPT → открыть Gemini → сравнить) — рутина, которая убивает время и не масштабируется.

**Что нужно:** инструмент, в котором несколько LLM обсуждают вопрос друг с другом — видят ответы оппонентов, спорят, пересматривают позиции, привлекают внешние данные. На выходе — не «один правильный ответ», а **карта аргументации**: что согласовано, что спорно, где пробелы в доказательности.

**Ключевое отличие от «просто сравнить ответы»:** агенты реагируют на аргументы друг друга. Раунд 2 качественно отличается от раунда 1 — позиции уточняются, слабые аргументы отбрасываются, появляются контрпримеры.

## 2. Пользователи и контекст

### 2.1. Пользователи (Фаза 1)

| Роль | Описание | Потребность |
|------|----------|-------------|
| Исследователь (владелец) | Аналитик, строит SciMap | Полный доступ, настройка, экспорт |
| Коллеги (2–3 чел.) | Учёные, не-разработчики | Веб-интерфейс, запуск дебатов, просмотр истории |

### 2.2. Типовые сценарии использования

**Сценарий A — Экспертный вопрос:**  
Пользователь спрашивает: «Каковы аргументы за и против OSL-датирования лёссов старше 100 тыс. лет?». Четыре агента дают независимые ответы, затем критикуют друг друга. На выходе — карта «за/против» с указанием, кто что аргументировал.

**Сценарий B — Сравнение подходов:**  
«Какую архитектуру выбрать для хранения claims: property graph, RDF, реляционная с JSONB?». Каждый агент защищает один подход (назначенные роли). Финал — сравнительная таблица с аргументами.

**Сценарий C — Верификация утверждения:**  
«Утверждение: "Валдайское оледенение не распространялось южнее 60° с.ш." — проверить». Модели ищут данные в интернете, приводят evidence за и против, оценивают надёжность.

**Сценарий D — Brainstorm:**  
«Как организовать кураторский контур для научного knowledge graph?». Режим consensus — цель не спор, а генерация и развитие идей.

**Сценарий E — Peer review текста:**  
Пользователь загружает фрагмент статьи/отчёта. Агенты выступают рецензентами: находят слабые места, противоречия, недостаточную аргументацию. Один агент может быть «защитником» текста.

### 2.3. Чем сервис НЕ является

- Не замена RAG-системе (не ищет по внутреннему корпусу документов)
- Не чат-бот (каждый дебат — отдельная задача с чётким входом/выходом)
- Не автоматический конвейер (пользователь контролирует процесс, может вмешиваться между раундами)
- Не инструмент для генерации текста (продукт — аналитика, а не «статья»)

## 3. Протокол дебатов

### 3.1. Базовая структура

```
ВВОД: вопрос + (опц.) контекст/документ + (опц.) выбор режима

РАУНД 0 (скрытый): web search
  → Если включён: все участники получают общий контекст из интернета
  → Контекст добавляется в системный промт каждого агента

РАУНД 1: независимые ответы
  → Вопрос → [Агент A, Агент B, Агент C, Агент D] параллельно
  → 4 независимых ответа (агенты НЕ видят друг друга)
  → Каждый ответ: позиция + аргументы + (опц.) источники

РАУНД 2+: перекрёстное рецензирование
  → Каждый агент видит АНОНИМИЗИРОВАННЫЕ ответы остальных (Response A/B/C/D)
  → Маппинг «Response A = claude-analyst» хранится на бэкенде, агенты не знают id оппонентов
  → Инструкция: «пересмотри позицию с учётом аргументов оппонентов»
  → Модель ОБЯЗАНА: (a) отметить, с чем согласна, (b) с чем не согласна и почему,
    (c) изменила ли свою позицию
  → Обязательно: найти минимум одно слабое место в КАЖДОМ ответе оппонента
  → Опц.: дополнительный web search по новым аргументам

СТОП-КРИТЕРИЙ:
  → max_rounds достигнут (настраивается, 1–5, default 3) ИЛИ
  → автодетект сходимости: позиции не изменились между раундами ИЛИ
  → пользователь остановил вручную

ФИНАЛ: синтез
  → LLM-судья (Sonnet / Opus):
    - Консенсус: в чём все согласны
    - Разногласия: в чём расходятся (и аргументы каждой стороны)
    - Оценка аргументации: чья позиция лучше подкреплена
    - Пробелы: что не было затронуто / требует дополнительных данных
    - (Опц.) рекомендация: если возможна
```

### 3.2. Формат ответа агента (гибридный JSON)

Каждый ответ агента в раунде 2+ — JSON с машиночитаемыми метаданными и свободным текстом аргументации:

```json
{
  "position": "Краткая формулировка позиции, 1–2 предложения",
  "confidence": "high | medium | low",
  "position_changed": true,
  "change_reason": "Аргумент Response B о ... убедил, потому что...",
  "agreements": [
    {"with": "Response A", "point": "описание пункта", "why": "свободный текст"}
  ],
  "disagreements": [
    {"with": "Response B", "point": "описание пункта", "counterargument": "свободный текст"},
    {"with": "Response C", "point": "слабое место аргумента", "counterargument": "свободный текст — обязательно для каждого оппонента"}
  ],
  "sources": ["url1", "url2"],
  "full_argument": "Свободный текст аргументации. Markdown допустим. Модель раскрывает позицию без ограничений формата..."
}
```

**Метаданные** (`position`, `confidence`, `position_changed`, `agreements`, `disagreements`) — парсятся автоматически, используются для метрик (convergence, position delta, stagnation) и UI (подсветка согласий/несогласий/смены позиции).

**`full_argument`** — отображается пользователю как основное содержание ответа.

**Раунд 1:** тот же JSON-формат, но поля `agreements`, `disagreements`, `position_changed` = пустые/false (агент ещё не видел оппонентов). Единый формат упрощает парсинг.

**Язык:** промты и ответы на русском. Ключи JSON — на английском (для парсинга). Если агент плохо следует JSON-инструкциям на русском — fallback: структурные ключевые слова промта на EN с требованием ответа на RU.

### 3.3. Вмешательство пользователя (Human-in-the-loop)

Между раундами пользователь может:

- **Добавить контекст:** загрузить документ, вставить цитату, уточнить условия
- **Перенаправить дискуссию:** «сфокусируйтесь на методических аспектах, а не на хронологии»
- **Исключить участника:** убрать агента, ответы которого неинформативны
- **Заменить агента:** переключить на другого агента с сохранением истории
- **Вбросить провокацию:** задать контраргумент от себя, чтобы агенты отреагировали
- **Остановить:** прервать и перейти к синтезу с тем, что есть

### 3.4. Автодетект сходимости

Критерии остановки (любой из):

1. **Семантическая стабильность:** позиция агента в раунде N+1 не отличается от раунда N (оценивается LLM-судьёй или cosine similarity сжатых позиций)
2. **Явный консенсус:** все агенты заявили согласие по основным пунктам
3. **Тупик:** агенты повторяют одни и те же аргументы без развития (зацикливание)

При автоостановке пользователь получает уведомление с причиной.

### 3.5. Анонимизация и анти-sycophancy

**Проблема:** агенты склонны соглашаться с убедительно звучащим ответом (sycophancy), особенно если знают brand оппонента. При схожих агентах дебат сходится к majority opinion, закрепляя общие заблуждения.

**Анонимизация для агентов — всегда.** Ответы оппонентов подаются как «Response A», «Response B», «Response C», «Response D». Маппинг хранится на бэкенде. Агенты не знают, кто написал какой ответ. Паттерн заимствован из LLM Council (Karpathy).

**Анонимизация для пользователя — опционально (toggle в UI, по умолчанию выкл).** Пользователю обычно полезно видеть, какой агент что сказал. Режим «слепой дебат» — для непредвзятой оценки.

**Контрмеры против sycophancy (встроены в промт раунда 2+):**

1. **Обязательный критический блок:** «Для КАЖДОГО ответа оппонента найди минимум одно слабое место — даже если в целом согласен. Если не можешь найти слабое место — объясни, почему аргумент безупречен.»
2. **Ротация роли скептика:** в каждом раунде один агент (по очереди) получает дополнительную инструкцию: «ты — критик в этом раунде, твоя задача — найти дыры в аргументации остальных».
3. **Метрика stagnation:** если все агенты согласились в раунде N без содержательных контраргументов — LLM-судья фиксирует красный флаг.

### 3.6. Управление контекстом раундов

**Принятое решение:** полная история всех раундов подаётся каждому агенту. Суммаризация не применяется.

**Расчёт для worst case (4 агента, 3 раунда, web search):**

```
Системный промт + инструкция:     ~1300 токенов
Вопрос + контекст пользователя:   ~2000 токенов
Web search (раунд 0):              ~2000 токенов
Раунд 1 (4 ответа × ~1500):       ~6000 токенов
Раунд 2 (4 ответа × ~2000):       ~8000 токенов
───────────────────────────────────────────────
Итого на входе раунда 3:          ~19300 токенов
```

~20K input — комфортно для всех frontier-моделей (128K+ контексты). При 5 раундах × 4 агента — до 40K, тоже в пределах.

**Стоимость типичного дебата (3 раунда, 4 агента):** ~$1–2 (при ценах Claude Sonnet / GPT-5.4). Приемлемо.

**Суммаризация предыдущих раундов** — отложена на Фазу 2, применяется только если дорастём до 5+ раундов с 5+ агентами.

## 4. Режимы дебатов

### 4.1. Debate (свободная дискуссия)

- Все участники равноправны
- Каждый формулирует и защищает свою позицию
- Системный промт: нейтральный, без навязывания стороны
- Подходит для: экспертных вопросов, «за и против», оценка рисков

### 4.2. Consensus (поиск согласия)

- Цель — найти общее, минимизировать разногласия
- Системный промт: «стремись к согласию, ищи точки соприкосновения»
- Финальный синтез фокусируется на «что мы выяснили» а не «кто прав»
- Подходит для: brainstorm, планирование, разработка подхода

### 4.3. Devil's Advocate (адвокат дьявола)

- Один агент **назначается оппонентом** — обязана оспаривать всё
- Остальные защищают тезис/позицию пользователя
- Системный промт оппонента: «твоя задача — найти слабые места, контрпримеры, скрытые допущения»
- Подходит для: проверка гипотез, подготовка к защите, стресс-тест идеи

### 4.4. Expert Panel (экспертная панель)

- Каждому агенту назначается **роль** (определяется пользователем или автоматически)
- Примеры ролей:
  - Доменный эксперт (геолог, историк, инженер...)
  - Методолог (критикует методы, не выводы)
  - Логик (проверяет структуру аргументации)
  - Скептик (требует evidence для каждого утверждения)
  - Синтезатор (не спорит, а собирает и структурирует)
- Роли задаются через системный промт
- Подходит для: сложные междисциплинарные вопросы, peer review

### 4.5. Peer Review (рецензирование)

- На вход подаётся **текст** (фрагмент статьи, отчёта, тезиса)
- Агенты выступают рецензентами
- Структура отзыва: основные замечания / второстепенные / предложения
- Опц.: один агент — «защитник» текста, парирует замечания
- Подходит для: подготовка публикаций, доработка текстов

### 4.6. Сравнение режимов

| Режим | Системный промт | Цель финального синтеза | Типовой max_rounds |
|-------|----------------|------------------------|--------------------|
| Debate | Нейтральный | Карта позиций + оценка | 3 |
| Consensus | «Ищи согласие» | Общий вывод | 2–3 |
| Devil's Advocate | Один — «оспаривай» | Устойчивость тезиса | 2–3 |
| Expert Panel | Роли | Экспертная оценка | 2–4 |
| Peer Review | «Рецензируй» | Список замечаний | 2 |

## 5. Поиск информации в интернете (Web Search)

### 5.1. Зачем

Без внешних данных дебат ограничен тем, что агенты «знают» (training data моделей). Для вопросов о текущих событиях, фактах, цифрах, свежих публикациях — это недостаточно. Web search делает дебат evidence-based.

### 5.2. Когда используется

| Ситуация | Web search |
|----------|-----------|
| Вопрос о фактах / текущих событиях | Автоматически (Раунд 0) |
| Пользователь явно запросил | Обязательно |
| Агент в раунде ссылается на «данные показывают...» без источника | По запросу агента (tool use) |
| Оппонент оспаривает факт — нужна проверка | По запросу агента |
| Абстрактный / философский вопрос | Не нужен |

### 5.3. Режимы web search

**A. Общий контекст (Раунд 0):**  
- Перед дебатом — поиск по ключевым словам вопроса
- Результаты (top-N snippets) добавляются как общий контекст ВСЕМ участникам
- Все агенты работают с одной и той же информационной базой

**B. По запросу агента (tool use в раундах):**  
- Модель в процессе ответа может вызвать web search
- Результат доступен только этому агенту (асимметричная информация)
- В ответе агент обязан указать источник
- Другие модели видят цитату+источник, могут проверить в следующем раунде

**C. По запросу пользователя (между раундами):**  
- Пользователь добавляет URL или поисковый запрос
- Результат добавляется как контекст ко всем моделям в следующем раунде

### 5.4. Требования к web search

- Каждый факт из web search должен сопровождаться URL источника
- Модель не может ссылаться на «исследования показывают» без конкретной ссылки
- При конфликте данных из разных источников — указывать оба
- Лимит: не более N поисков на раунд на модель (настраивается, default 3)
- Трекинг: какие поисковые запросы выполнены, какие результаты использованы

## 6. Финальный синтез

### 6.1. Структура синтеза

Финальный синтез — отдельный документ, генерируемый после последнего раунда. Структура:

```
1. ВОПРОС И КОНТЕКСТ
   Исходный вопрос, контекст, режим, участники, количество раундов

2. КОНСЕНСУС
   Что все модели в итоге считают верным/обоснованным
   Для каждого пункта: кто первым предложил, кто присоединился

3. РАЗНОГЛАСИЯ
   По каждому спорному пункту:
   - Позиция A: [модель(и)] — аргументы
   - Позиция B: [модель(и)] — аргументы
   - Ключевой контраргумент каждой стороны
   - Что нужно для разрешения (данные? эксперимент? уточнение?)

4. ЭВОЛЮЦИЯ ПОЗИЦИЙ
   Кто изменил позицию и почему (с указанием раунда)
   Какие аргументы оказались наиболее убедительными

5. ОЦЕНКА АРГУМЕНТАЦИИ
   Качественная оценка: чья аргументация была сильнее и почему
   Обнаруженные логические ошибки / слабые места

6. ПРОБЕЛЫ И РЕКОМЕНДАЦИИ
   Что не было затронуто
   Какие данные/исследования помогли бы разрешить разногласия
   Рекомендуемые следующие шаги

7. ИСПОЛЬЗОВАННЫЕ ИСТОЧНИКИ
   Сводный список всех URL и ссылок из всех раундов
```

### 6.2. Кто делает синтез

Варианты (настраивается):

- **Судья** (по умолчанию): Sonnet 4.6 (Фаза 0) / Opus 4.6 (если нужно), не участвовавший в дебате, видит все раунды, делает нейтральный анализ
- **Один из участников**: назначенная модель суммирует (риск предвзятости)
- **Консенсусный**: каждая модель делает свой синтез → мердж

### 6.3. Формат выхода

- Markdown (основной)
- Экспорт в PDF (для шаринга)
- JSON (структурированный, для программной обработки / интеграции с SciMap)

## 7. Метрики и оценка качества

### 7.1. Зачем нужны метрики

Без метрик невозможно ответить на вопрос: «А дебат вообще полезнее, чем просто спросить одну модель?». Метрики нужны для:
- Оценки ценности конкретного дебата
- Выбора оптимальных настроек (количество раундов, состав моделей)
- Сравнения моделей между собой
- Обоснования затрат (токены/деньги vs польза)

### 7.2. LLM-судья (с Фазы 0)

LLM-судья — Фаза 0: **Claude Sonnet 4.6** (проверяем, хватит ли качества). Если синтез/вердикты неудовлетворительны — переход на **Opus 4.6** (output небольшой: ~500 токенов вердикт, ~2000 синтез — стоимость ~$0.15/дебат).

**Примечание:** судья и агенты claude-analyst/claude-creative используют одну модель (Sonnet), но это не проблема — у судьи другой системный промт, другая температура (0.2 vs 0.3/0.8), и он не участвует в дебате. Разделение ролей обеспечивается промтами, не моделями.

Судья вызывается: (a) после каждого раунда (для автодетекта сходимости и stagnation), (b) после завершения дебата (для метрик качества и финального синтеза).

Судья оценивает:
- Появились ли новые аргументы (argument novelty)
- Изменились ли позиции содержательно (position delta)
- Есть ли зацикливание (stagnation)
- Качество аргументации каждого участника (для финального синтеза)

### 7.3. Метрики процесса (автоматические)

| Метрика | Что измеряет | Как считается |
|---------|-------------|---------------|
| Convergence rate | Сходимость позиций | % пунктов, по которым достигнут консенсус |
| Position delta | Изменение позиций | Количество моделей, сменивших позицию |
| Argument novelty | Новизна аргументов | Доля новых аргументов в раунде N vs N-1 |
| Evidence density | Насыщенность доказательствами | Количество ссылок/источников на ответ |
| Round utility | Полезность раунда | Сколько новой информации добавил раунд (оценивается LLM-судьёй) |
| Stagnation detector | Зацикливание | Повторение аргументов без развития |

### 7.4. Метрики качества (экспертная/пользовательская оценка)

| Метрика | Что измеряет | Как оценивается |
|---------|-------------|----------------|
| Depth | Глубина анализа | Пользователь: «Узнал ли я то, чего не знал?» (1–5) |
| Fairness | Сбалансированность | Были ли представлены все значимые точки зрения? (1–5) |
| Actionability | Практичность | Можно ли на основе синтеза принять решение? (1–5) |
| Debate > Single | Превосходство над одиночным ответом | «Дал ли дебат больше, чем ответ лучшей модели?» (да/нет/не уверен) |

### 7.5. Экономические метрики

| Метрика | Что измеряет |
|---------|-------------|
| Tokens per debate | Суммарные токены (input + output, по моделям) |
| Cost per debate | Стоимость в $ (по тарифам провайдеров) |
| Cost per round | Стоимость раунда (для оценки «стоит ли ещё раунд?») |
| Cost per insight | Субъективная: стоимость / оценка Depth (руб./балл) |
| Budget remaining | Остаток бюджета дебата (если задан лимит) |

### 7.6. Сравнение моделей (побочный продукт)

По итогам N дебатов накапливается статистика:

- Как часто модель X меняла позицию (гибкость vs упрямство)
- Как часто аргументы модели X признавались убедительными другими
- Средняя evidence density по модели
- Средняя оценка качества аргументации по модели
- Стоимость/токен по модели (efficiency)

Не является целью сервиса, но ценный побочный продукт.

### 8.2. Управление дебатом

- Запуск дебата (создание новой сессии)

- Ручная остановка + переход к синтезу
- Повторный запуск раунда (если ответ неудовлетворительный)

### 8.3. Вывод и экспорт

- Отображение раундов: параллельно (колонки) или последовательно
- Финальный синтез: отдельный блок
- Экспорт в Markdown (полный лог + синтез)
- Экспорт в JSON (структурированный, для программной обработки)
- Экспорт в PDF (для шаринга)
- Копирование отдельного ответа / синтеза в буфер

### 8.4. История

- Сохранение всех дебатов с полной историей раундов
- Поиск по истории (по тексту вопроса, дате, режиму, участникам)
- Повторный запуск дебата с другими настройками (fork)
- Удаление дебата

### 8.5. Управление моделями

- Список доступных моделей с провайдером и ценой
- Добавление/удаление моделей (конфигурация)
- API-ключи: хранение, валидация, ротация
- Статус доступности моделей (health check)

## 9. Нефункциональные требования

### 9.1. Производительность

- Раунд 1 (3 параллельных вызова): начало стриминга ≤5 сек
- Время раунда: определяется самой медленной моделью (типично 15–60 сек)
- Web search: ≤10 сек на запрос
- Финальный синтез: ≤60 сек

### 9.2. Надёжность

- Если одна модель упала / timeout: дебат продолжается с оставшимися (минимум 2)
- Если API-ключ невалиден: уведомление + исключение модели
- Retry: 1 повтор при timeout, 0 повторов при ошибке контента
- Состояние дебата персистентно: перезагрузка сервера не теряет текущий дебат

### 9.3. Безопасность

- API-ключи: хранятся зашифрованно, не отображаются в UI после ввода
- Аутентификация: простая (логин/пароль или токен) для доступа к веб-интерфейсу
- Нет публичного доступа без аутентификации

### 9.4. Масштабируемость (Фаза 1)

- 1–3 одновременных дебата
- 3–4 пользователя
- История: до 1000 дебатов
- Не требуется: горизонтальное масштабирование, CDN, кэширование

## 10. Доступ к моделям и биллинг

### 10.1. Ключевое ограничение: подписки ≠ API

Подписки на чат-интерфейсы (Claude Max, ChatGPT Plus/Pro, Gemini Advanced) **не дают программного API-доступа**. Это отдельные продукты с отдельной оплатой у всех провайдеров. Anthropic в январе 2026 явно заблокировала попытки использовать OAuth-токены подписки для API-вызовов из сторонних приложений (включая OpenClaw). Workaround'ы (CLIProxyAPI, перехват OAuth) несут риск бана аккаунта.

Для LLM Debate это означает: **только API-ключи, никаких обходов подписок.**

### 10.2. Принятое решение: прямые API-ключи + LiteLLM

Используются прямые ключи провайдеров, маршрутизация через LiteLLM (единый интерфейс, OpenAI-совместимый API).

| Провайдер | Модель | Агенты | Роль |
|-----------|--------|--------|------|
| Anthropic | Claude Sonnet 4.6 | claude-analyst (t=0.3), claude-creative (t=0.8) | Участники + судья |
| OpenAI | GPT-5.4 | gpt-critic (t=0.4), gpt-generalist (t=0.6) | Участники |


**Отброшен OpenRouter:** лишняя прослойка и наценка при наличии собственных ключей. Может быть добавлен позже как fallback.

### 10.3. Модель для пользователей

Все пользователи работают через общие ключи владельца (Фаза 1 — 3–4 человека, бюджет контролируемый).

- **Владелец:** полный доступ ко всем моделям, настройка конфигурации
- **Коллеги:** доступ к набору моделей, определённому владельцем; лимит на дебаты/день (настраивается)

При масштабировании (Фаза 2+): возможен переход на BYOK (каждый со своим ключом).

## 12. Failure Modes и обработка ошибок

| Ситуация | Поведение |
|----------|-----------|
| Агент не ответил (timeout >120 сек) | Пометить «[Агент X]: нет ответа (timeout)», продолжить раунд |
| Агент отказался отвечать (content policy) | Показать отказ, продолжить с другими |
| Все агенты отказались | Завершить дебат, показать причины отказа |
| Web search недоступен | Предупредить, продолжить без поиска |
| API rate limit | Очередь + уведомление о задержке |
| Бюджет превышен | Остановить, перейти к синтезу с имеющимися раундами |
| Ответ агента не соответствует структуре | Принять as-is, отметить «неструктурированный» |
| Зацикливание (3+ раунда без изменений) | Автостоп + уведомление + синтез |
| Один агент доминирует (другие «соглашаются» без аргументов) | Предупреждение в метриках, возможно — переключение режима |

## 13. Связь с SciMap (будущая интеграция)

Не реализуется в Фазе 1, но архитектура должна допускать:

### 13.1. SciMap: верификация claims

- Вход: claim из SciMap (текст + evidence + chunk_refs)
- Режим: devil_advocate (одна модель защищает claim, остальные атакуют)
- Выход: verdict (подтверждён / опровергнут / недостаточно данных) + обоснование
- Привязка результата к claim в SciMap (через API)

### 13.2. SciMap: кросс-анализ дискуссионных тем

- Вход: группа дистиллятов по спорной теме
- Режим: expert_panel (каждая модель = специалист по эпохе/региону/методу)
- Выход: карта разногласий с привязкой к конкретным публикациям

### 13.3. Требования к API для интеграции

- REST API уже реализован в Фазе 1 (Фаза 0 — только CLI)
- Вход: JSON (вопрос, контекст, настройки)
- Выход: JSON (полный лог + синтез)
- Webhook или polling для асинхронного получения результата

## 14. Фазы реализации

### Фаза 0: Прототип (1–2 недели)

- CLI-интерфейс: вопрос → 4 агента → 2–3 раунда → синтез → Markdown
- 1 режим (Debate)
- Гибридный JSON-формат ответов (§3.2)
- Анонимизация ответов (Response A/B/C/D)
- LLM-судья после каждого раунда + финальный синтез
- Web search добавляется к концу Фазы 0 (шаг 8)
- Без UI
- Цель: валидация концепции, итерация по промтам, оценка стоимости

**Критерий успеха:** дебат из 3 раундов по научному вопросу даёт синтез, который исследователь оценивает как «полезнее одиночного ответа».

### Фаза 1: Рабочий инструмент (3–4 недели)

- Веб-интерфейс
- Все 5 режимов
- Web search (раунд 0 + tool use)
- Стриминг, история, экспорт
- Метрики процесса (автоматические)
- 3–4 пользователя
- REST API для программного доступа

**Критерий успеха:** коллеги используют самостоятельно, средняя оценка Depth ≥3.5/5.

### Фаза 2: Интеграция (по необходимости)

- Подключение к SciMap (верификация claims)
- Подключение к SciMap (кросс-анализ)
- Пользовательские промт-шаблоны для специфических задач
- Расширенные метрики и аналитика по истории дебатов

## 16. Предшественники и источники

### 16.1. Научная основа

| Работа | Ключевой вывод | Как используем |
|--------|---------------|----------------|
| Du et al., «Improving Factuality and Reasoning through Multiagent Debate» | Дебат между экземплярами LLM улучшает фактуальность и reasoning | Базовый паттерн: N моделей → K раундов → синтез |
| Khan et al., «Debating with more persuasive LLMs leads to more truthful answers» (ICML 2024 Best) | Разнородные по силе модели дают более правдивые результаты | Обоснование мульти-провайдерного состава |
| «Multi-LLM Debate: Framework, Principals, and Interventions» (OpenReview 2024) | При схожих агентах дебат сходится к majority opinion; общие заблуждения из training data закрепляются | **Критическое предупреждение:** необходимы разнородные модели + web search для внешних фактов |

### 16.2. Открытые проекты — что берём

| Проект | Автор/орг | Что заимствуем | Что НЕ подходит |
|--------|-----------|---------------|-----------------|
| **LLM Council** | Karpathy (2025) | Архитектура UI (FastAPI+React), анонимизация при peer review, 3-stage workflow | 1 раунд (нет итеративного дебата), нет web search, нет режимов, заброшен, привязан к OpenRouter |
| **DebateLLM** | InstaDeep (2024) | Промт-стратегии для разных протоколов дебата (несколько паттернов, протестированных на Q&A) | Single-model (GPT-3.5), нет UI, нет мульти-провайдерности, Hydra-конфиг |
| **MAD** | Liang et al. (2023) | Архитектура «affirmative/negative + judge» → режим Devil's Advocate | Одна модель, нет web search, исследовательский скрипт |
| **LLM Agora** | gauss5930 (2023) | Evidence что разнородные open-source LLM дают синергию + CoT поверх дебата | Неактивен, нет UI, ограничен open-source моделями |

### 16.3. Что делает наш проект уникальным

Ни один из существующих проектов не совмещает:
- Мульти-провайдерность (разные модели от разных вендоров в одном дебате)
- Итеративные раунды с human-in-the-loop
- Web search как источник evidence в процессе дебата
- Несколько режимов (debate / consensus / devil's advocate / expert panel / peer review)
- Метрики качества дебата
- Веб-интерфейс для не-разработчиков
